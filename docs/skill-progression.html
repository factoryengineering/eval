3. Why values-only moved

StepWhat changedWhy
1 to 2 Skill text: "Do not use AsNoTracking(); project values from read-only queries." became "Read-only queries project values, never entities, so nothing is tracked: never write AsNoTracking()." A bare prohibition lost to the model's habit of adding AsNoTracking() to anything described as read-only. Giving the reason raised the rate from 0.33 to 0.60.
2 to 3 Grader only: read-only-values now accepts tuple projections such as select (post.Title, post.Views). Every remaining failure was a correct answer the regex did not recognise. The skill text did not change, and the measured rate rose from 0.60 to 1.00.

Step 3 is a measurement fix, not a skill improvement. Of the 0.33 to 1.00 total, the skill-text change accounts for the 0.33 to 0.60 portion; the rest is the grader being corrected.

6. The rest of the story

Steps 1 to 4 were not the end. Sections 1 to 5 describe the state at commit 67b1112; the later commits (PROGRESS.md Iterations 5 to 22) changed several of their conclusions.

PhaseIterationsWhat happened
C: dead weight5 to 8 The full-skill baseline showed project, translatable and async at 1.00 without the line. Causes were weak cases and a grader that only checked ToListAsync(, not the token. Cases were hardened (async 0.00 to 1.00, split-query 0.00 to 1.00), project was deleted as redundant with values-only, and translatable was rewritten three times to ban user-defined helpers and post-materialization filters (0.00 to 1.00). Three-model confirmation: 19 of 21 line-model cells load bearing.
B2: probes9 Hypothesis: values-only breaks write paths that need a tracked entity. Rejected. Models read "read-only" as the scope. The one failure was prose mentioning AsNoTracking(), so grading was limited to fenced code. No new skill text.
D: description10 to 11b A trigger eval for the frontmatter description. Positives saturated even with a name-only description, so the spec moved to near-miss negatives (LINQ to objects, raw SQL, Dapper). The actions clause was dead weight and was dropped. Description is now "Opinions for LINQ queries against an Entity Framework Core DbContext. Not for migrations, model configuration, or raw SQL." It beats name-only by +0.06 to +0.20 on five models.
E: neutral directory12 to 13 Runs moved to an empty temp directory so the model could not see the real skill. Regression checks became guard cases that do not dilute line deltas. SWE-1.7 and SWE-2 joined, and all lines passed 100% with the skill on 5 models. Rule ids were moved to a sidecar file so the shipped SKILL.md is clean and byte-identical to what was tested.
F: executable graders17 to 22 Regexes were replaced by oracles: Roslyn compile, run on seeded SQLite, assertions on executed SQL, syntax-tree checks, and a calibrated LLM judge for identifier names. Graders are themselves tested against good and bad reference solutions.

7. The twist: the earlier result was partly wrong

Under compile-and-run graders, the "all lines at 1.00" result from the regex era did not hold. Iteration 17 found three causes in the compiler errors:

  • Test noise: models invented types such as PostSummary. The prompts were fixed. A first fix that told the model to define its own types made every model redefine BlogContext, so every cell scored 0.00. That run was discarded.
  • The step 3 fix was wrong. Tuple projections like select (post.Title, post.Views) raise CS8143 inside an expression tree. They are valid only after materialisation. Widening the values-only regex hid a real failure instead of fixing a grader false negative. Section 3 and its note are superseded.
  • A rule interaction no regex could see: query syntax, meaningful names and a separate statement together led models to write from post in posts then var post = await ..., which fails with CS1931. The edit guard failed on all five models, 0.00 to 0.80.

The fix was a new line, distinct-result-name: "Give the awaited result a different name from the query's range variable." Adding a concrete example to it did not help, so it was reverted to the shorter text.

The shipped skill went from 5 lines (Iteration 0) to 8 rules. The earlier project line was deleted and no-tracking was replaced. The rules split-query, async and translatable were kept, and distinct-result-name was added.

The meaningful-names judge was calibrated first. A rubric with an unstated "generic placeholder" clause split four judge models on 7 of 24 ordinary words. After the rubric was changed to mirror the skill's wording, all four judges matched 59 of 59 hand-labelled identifiers. Sonnet is the default judge, and it only labels bare identifier strings.

Caveats

  • Sections 1 to 5 are the original snapshot at 67b1112: one model, regex graders, 3 to 5 trials. Section 3's grader fix is retracted in section 7, and the Iteration 1 to 16 rates should not be compared with Iterations 17 to 22.
  • The trigger eval spec was revised twice after seeing results, so its final numbers are likely optimistic. It has not been re-measured under the final graders, though it does not use them.
  • The judge calibration labels were written by the repository author and cover clear cases only. Sonnet is both a model under test and the default judge.
  • 5-trial cells are coarse, so deltas of 0.2 are noise. 10 and 30 trial cells are marked.
  • Token counts are estimates because the Devin CLI reports no usage.
