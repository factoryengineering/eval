---
name: idempotent-writes
description: Opinions for retry-safe and concurrency-safe create, update and delete endpoints on an ASP.NET Core and EF Core API, covering client-chosen ids, ETag and If-Match, and tombstones. Not for read-only endpoints, other frameworks, or general API style.
---
Rules for retry-safe write endpoints:
- Take a client-chosen GUID `id` in the POST body and never generate public ids on the server; the first create answers 201 with `Location` and `ETag`, repeating the same create (same id, same content) answers 200 with the current representation instead of an error, only the same id with different content is 409, and a missing id is 400.
- Make the ETag the quoted, unpadded base64url SHA-256 of a canonical form built from the parsed client-writable values (the id, the parent id and the writable fields in fixed order; compact JSON, lowercase GUIDs, NFC-normalized strings, numbers without trailing zeros), never from the raw request body, so two spellings of the same content give the same ETag; never hash counters, analytics, timestamps or other server-maintained or derived values, and never let them invalidate `If-Match`.
- Put a unique index on the public GUID (`HasAlternateKey` or a unique `HasIndex`) and create by inserting first: catch the `DbUpdateException`, detach the entity, read the existing row with `IgnoreQueryFilters()` and classify the unique violation; never query first and insert after, because concurrent creates race through the gap.
- Store the ETag in a non-null string column configured with `IsConcurrencyToken()` and set it on every write; never use a row version, `[Timestamp]`, `IsRowVersion()` or a sequence number as the ETag or as the concurrency token.
- Store the hash of the create request in a non-null column configured with `Metadata.SetAfterSaveBehavior(PropertySaveBehavior.Throw)` (`using Microsoft.EntityFrameworkCore.Metadata;`) and never update it, so a replay can still be told from a conflict after later updates.
- Delete by setting a nullable `DeletedAt` tombstone behind a global `HasQueryFilter` and make `DeletedAt` a concurrency token next to the ETag, so a DELETE and a PUT racing from the same ETag serialise (one wins, the other gets 412 or 410) instead of the PUT writing to a tombstoned row; tombstone dependants in the same transaction.
- Treat a PUT whose body hash already equals the stored ETag as already applied and answer 204 with that ETag whatever `If-Match` says, checking it before the `If-Match` comparison and again after a `DbUpdateConcurrencyException`, so retries and two identical racing PUTs both succeed; answer 412 with the current ETag only when the stored state really differs.
- Answer DELETE of an unknown or already tombstoned item with 204, never 404 or 410, while a missing `If-Match` is still 428 and a live item with a stale `If-Match` is 412; on a `DbUpdateConcurrencyException` re-read and re-evaluate once instead of returning 500.
