## Iteration A5 - races and lost responses

- 2026-11-11T05:30:00.000Z Scope: deterministic concurrency and lost-response conformance. No change to what the earlier scenarios assert. Also fixed on the A4 hash-vector line the stray backtick and duplicated phrase (typo only).
- Interleaver (`dotnet/ApiConformance/Interleaver.cs`): the host adds an ASP.NET middleware that reads `X-Test-Participant` into an `AsyncLocal`, and, after the generated `AppSetup.ConfigureServices`, `services.ConfigureDbContext<TContext>(o => o.AddInterceptors(command, transaction))` for every DbContext type of the generated assembly (EF Core 9+; no cooperation from the generated code). Justification: first tried registering `IInterceptor` singletons in the application service provider; the interceptors were never invoked (the event log stayed empty while the app still ran), so reflection over `ConfigureDbContext<T>` is used. Every DbCommand (reader, non-query, scalar, sync and async) and every `TransactionStarting` passes `Before`; SaveChanges needs no interceptor of its own because it only issues commands and a transaction.
- Gate rules: participants start sequentially (the next request starts only when the previous one is parked at its first command or done), then all participants advance command by command; a round is released when nobody is still running. SQLite serialises writers, so the gate models that: a write command (INSERT/UPDATE/DELETE/REPLACE) or `BEGIN` is granted the single write lock by the gate; the other participant waits (counts as arrived) until the holder's transaction commits/rolls back, its autocommit statement ends, or its request finishes. No timers drive the schedule; the only timer is the hard timeout (20 s per race, `ScenarioFailure` with the participant states and the event log). Lowest participant id wins ties, so the schedule is a pure function of the app's command sequence.
- Decision (evidence): EF Core 10 on SQLite begins transactions with `BEGIN IMMEDIATE`, so the lock is taken when the transaction starts, before the first command. My first gate only modelled commands; the parent-delete race (two commands in one transaction) hung with both a shared-cache and a file database (state: `0=Running, 1=Waiting before [UPDATE ...]`); fixed by modelling `TransactionStarting` as a write.
- Decision (evidence): host database. With the gate fixed, all five good references passed on the in-memory shared-cache database, but a minimal two-request app (one multi-statement transaction, one reader, `InterleaverTests`) hung 2 of 60 iterations on shared cache (table-level SQLITE_LOCKED blocks a reader while the writer waits at the gate) and 0 of 60 on a WAL file database. The host now uses a per-host temporary file database (`Data Source=<tmp>/apiconformance-<guid>.db;Pooling=False;Default Timeout=30`, `PRAGMA journal_mode=WAL` through the keeper connection), deleted with its -wal and -shm files on dispose. The host also maps an unhandled exception to a 500 text response (as Kestrel would) so a broken mutant surfaces as a 5xx instead of an exception in the client.
