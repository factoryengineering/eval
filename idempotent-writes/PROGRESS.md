## Iteration A5 - races and lost responses

- 2026-11-11T05:30:00.000Z Scope: deterministic concurrency and lost-response conformance. No change to what the earlier scenarios assert. Also fixed on the A4 hash-vector line the stray backtick and duplicated phrase (typo only).
- Interleaver (`dotnet/ApiConformance/Interleaver.cs`): the host adds an ASP.NET middleware that reads `X-Test-Participant` into an `AsyncLocal`, and, after the generated `AppSetup.ConfigureServices`, `services.ConfigureDbContext<TContext>(o => o.AddInterceptors(command, transaction))` for every DbContext type of the generated assembly (EF Core 9+; no cooperation from the generated code). Justification: first tried registering `IInterceptor` singletons in the application service provider; the interceptors were never invoked (the event log stayed empty while the app still ran), so reflection over `ConfigureDbContext<T>` is used. Every DbCommand (reader, non-query, scalar, sync and async) and every `TransactionStarting` passes `Before`; SaveChanges needs no interceptor of its own because it only issues commands and a transaction.
- Gate rules: participants start sequentially (the next request starts only when the previous one is parked at its first command or done), then all participants advance command by command; a round is released when nobody is still running. SQLite serialises writers, so the gate models that: a write command (INSERT/UPDATE/DELETE/REPLACE) or `BEGIN` is granted the single write lock by the gate; the other participant waits (counts as arrived) until the holder's transaction commits/rolls back, its autocommit statement ends, or its request finishes. No timers drive the schedule; the only timer is the hard timeout (20 s per race, `ScenarioFailure` with the participant states and the event log). Lowest participant id wins ties, so the schedule is a pure function of the app's command sequence.
- Decision (evidence): EF Core 10 on SQLite begins transactions with `BEGIN IMMEDIATE`, so the lock is taken when the transaction starts, before the first command. My first gate only modelled commands; the parent-delete race (two commands in one transaction) hung with both a shared-cache and a file database (state: `0=Running, 1=Waiting before [UPDATE ...]`); fixed by modelling `TransactionStarting` as a write.
- Decision (evidence): host database. With the gate fixed, all five good references passed on the in-memory shared-cache database, but a minimal two-request app (one multi-statement transaction, one reader, `InterleaverTests`) hung 2 of 60 iterations on shared cache (table-level SQLITE_LOCKED blocks a reader while the writer waits at the gate) and 0 of 60 on a WAL file database. The host now uses a per-host temporary file database (`Data Source=<tmp>/apiconformance-<guid>.db;Pooling=False;Default Timeout=30`, `PRAGMA journal_mode=WAL` through the keeper connection), deleted with its -wal and -shm files on dispose. The host also maps an unhandled exception to a 500 text response (as Kestrel would) so a broken mutant surfaces as a 5xx instead of an exception in the client.
- Decision (flake found by the 20x soak, fixed): the first soak run had `race-create-same-id-same-body-both-succeed` fail 2 of ~660 runs with two 500s `No property found that maps to constructor parameter 'Id' for type 'PostBody'`: both requests were doing cold ASP.NET model-binding metadata initialisation of a fresh host at the same moment, before any database command. The interleaver now starts participants sequentially (second request starts when the first is parked), which removes pre-database concurrency entirely. Re-run: zero flakes (below).

- Scenarios (every ETag is compared with the harness `CanonicalHash`; replays use a different spelling of the same create and must be 2xx with the same ETag): canonical-property-order-does-not-change-etag (reversed property order), canonical-whitespace-does-not-change-etag (CRLF, tabs, spaces around separators), canonical-nfd-strings-same-etag-as-nfc-and-replay-succeeds, canonical-uppercase-guids-same-etag-and-identity (uppercase id, parent id in body and route; GET with lowercase and uppercase route; lowercase replay), canonical-number-spellings-same-etag (`12.5`, `12.50`, `1.250000E+001`, `0.5`), canonical-different-ids-have-different-etags, canonical-changing-any-writable-field-changes-etag (PUT per field, bool included, PUT and GET ETag equal the hash), canonical-etag-shape-is-quoted-base64url-sha256 (`^"[A-Za-z0-9_-]{43}"$` on create, GET, PUT), canonical-escaped-characters-hash-and-round-trip (quote, backslash, U+0007, tab, emoji, `x` + U+0301, which has no precomposed form so the GET value must be unchanged), canonical-etag-is-stable-across-gets-and-no-op-put.
- Descriptor-driven: the NFD and escape scenarios only exist when a string field is writable and use the first string field only (other string fields can be enumerations or validated; support's `category` rejected a decorated value and logistics rejects more than 2 decimals, so the first run of these two scenarios failed in the harness, not in the references; the harness was narrowed, not the references). The number scenario exists only for fields whose `clrType` is Decimal, Double or Single (logistics only; integer fields cannot carry `12.50` through a typed binder, so blog and support have 9 canonical scenarios, logistics 10).
- Ambiguities (safest interpretation): braces-free or hyphen-free GUID spellings (`N` format) are not accepted by the System.Text.Json binder, so only uppercase is tested. Round trip of NFD input through GET is not asserted (a service may return the NFC form); only the ETag and the replay are.
- Good references: all five descriptors pass the new group with no reference change. No reference fix was needed.
- Harness change: `Mutant` gained an optional `extra` list of edits (`Subject.Apply`), because the raw-body mutants need controller and service edits. Test helper only.
- Mutants (blog posts unless stated; recorded sets include only canonical-* or ETag-comparison scenarios, reviewed one by one):
  - etag-property-order-sensitive: canonical-property-order-does-not-change-etag only (controller captures the sent property order, hash follows it; the replay then 409s). Ported: support-etag-property-order-sensitive (same single scenario).
  - etag-no-nfc: canonical-nfd-strings-same-etag-as-nfc-and-replay-succeeds only.
  - etag-guid-case-sensitive: canonical-uppercase-guids-same-etag-and-identity only (id hashed as sent). First run also failed create-missing-id-is-bad-request (GetProperty threw on a missing id); mutant rewritten with TryGetProperty.
  - etag-raw-body-hash: order, whitespace, nfd, uppercase guid, escaped-characters (the harness bodies are canonical ASCII, so plain scenarios still pass). Ported: support-etag-raw-body-hash (same five).
  - etag-trailing-zero-numbers (logistics): canonical-number-spellings-same-etag plus every scenario that compares an ETag built from sample 0 (12.50), 13 in total.
  - etag-md5-or-wrong-encoding (padded standard-alphabet base64; internally consistent so If-Match flows still work) and etag-includes-whitespace: 20 and 19 scenarios, all ETag-versus-hash comparisons; etag-shape fails only for the encoding mutant, as it should.
  - Not a mutant of a different algorithm (MD5 hex) because any wrong hash fails the same ETag comparisons.
- Existing mutants re-recorded after seeing the run (15 of 33; replay-409, logistics-replay-409, no-unique-index, wrong-etag, server-generates-id, hash-includes-server-owned): only canonical-* scenarios were added, none dropped; they exercise the same defect (for example replay-409 fails every canonical replay).

## Iteration A7 - static facts

- 2026-11-11T05:10:00.000Z Scope: `StaticChecks` in `dotnet/ApiConformance` (`StaticChecks.cs`, `.Model.cs`, `.Source.cs`): named checks `{Id, Passed, Evidence, Advisory}` over the generated sources (own Roslyn compilation with semantic models via `GeneratedApp.CreateCompilation`), the compiled assembly and the started `ApiHost` (`DbContext.Model` plus SQLite `PRAGMA table_info/index_list/index_info/foreign_key_list`). Test side: `StaticCheckTests`.
- Domain neutrality: `DomainDescriptor` and `ParentDescriptor` gained an optional `entityTypeName` (resource and parent entity); the five descriptors set it. Without it every entity type with a Guid property is a resource. The checks read the descriptor's existing `serverOwned` list.
- EF model/schema checks (IModel, never text): public-id-unique-index (unique index or alternate key on a non-key Guid property, and a unique index with that column in the SQLite schema), internal-key-int-hidden (single int/long primary key, every SQLite foreign key references the principal's integer key, combined with the Roslyn exposure facts: no id-like route parameter, action parameter or request/response property is int/long), etag-concurrency-token, no-rowversion-etag ([Timestamp], value generated on update, or an int/byte[] concurrency token; a nullable DateTime tombstone token is allowed), creation-hash-immutable (non-null string with AfterSaveBehavior Throw or Ignore), tombstone-property (nullable timestamp referenced by the declared query filter), etag-column-not-null (PRAGMA notnull on the string concurrency token columns), server-owned-not-concurrency-token.
- Roslyn checks: routes-use-guid, no-entity-in-responses (return types and arguments of ControllerBase helpers and `new ObjectResult`, unwrapped through Task, generics and arrays, compared with the model's entity CLR names), no-int-id-in-dtos (DTOs are non-entity source types used by actions), sha256-used-for-etag (symbol resolution of System.Security.Cryptography types; MD5, SHA1 or any GetHashCode call fails), etag-header-set (POST, PUT and GET-with-route-parameter actions assign or append the ETag header), if-match-required (PUT and DELETE: `[FromHeader(Name="If-Match")]`, or the string "If-Match" or `IfMatch` in the action), cancellation-token-passed (async actions take a CancellationToken and pass it as an argument of an awaited call), problem-details-used, no-check-then-insert (advisory).
- Heuristic for no-check-then-insert: a method that calls `DbSet<T>.Add/AddAsync`, has no catch of DbUpdateException (or Exception or a bare catch), and earlier calls Any/FirstOrDefault/SingleOrDefault/Count/ContainsAsync on a queryable of the same entity type T. Reported with `Advisory = true`; `StaticChecks.Failing` ignores it, so it can never be the sole failure reason. No false positive on the five good references (the parent lookup in a child create is another entity type, and creates have the DbUpdateException handler); flagged on check-then-insert and logistics-check-then-insert, tested.
- Good references: all five descriptors pass all 17 checks, no reference change.
